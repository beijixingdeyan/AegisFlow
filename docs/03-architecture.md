## 1. 三平面架构与通信安全边界

```
┌──────────────────────────────────────────────────────────────────────────┐
│  Management Plane  (管理平面)                                              │
│  · UI / REST API (`api/serve.py`)   · RBAC+ABAC (`security/access.py`)    │
│  · 配置 (`config.py`)              · 审计 (`security/audit.py`)           │
└───────────────────────────────┬──────────────────────────────────────────┘
                                │ 双向 mTLS  (内部所有组件互证身份)
┌───────────────────────────────▼──────────────────────────────────────────┐
│  Control Plane  (控制平面)                                                 │
│  · 策略管理 · AI 推理 (`detection/intelligence.py`) · 决策引擎             │
│  · DetectionPipeline: 基线→异常→规则→推理→解释 (`detection/pipeline.py`)    │
└───────────────────────────────┬──────────────────────────────────────────┘
                                │ 双向 mTLS · 批量消费 (背压/熔断/重试)
┌───────────────────────────────▼──────────────────────────────────────────┐
│  Data Plane  (数据平面)                                                    │
│  · 采集 (无状态, 可水平扩展)   · 归一化+脱敏 (`dataplane/ingestion.py`)     │
│  · 高可用事件总线 (`bus/resilient_queue.py`)：背压、熔断、重试、批量        │
└──────────────────────────────────────────────────────────────────────────┘
```

**关键点**：三平面职责分离；每一条内部调用都经 mTLS 双向认证（`MTLSTransport`），
无隐式信任；控制平面不直连外部流量；数据平面不接触明文 PII（接入即脱敏）。

## 2. 高可用设计（99.99% SLA · Active-Active）

### 2.1 多活（Active-Active）
- **核心处理节点无状态**：`DetectionPipeline`、`Ingestor`、`ResponseOrchestrator` 均不持有跨请求
  持久状态（行为基线可放 Redis/内存 + 定期快照），任一节点可随时增减。
- **多分区消费**：事件总线（生产可用 Kafka/NATS，本仓库提供 `ResilientBus` 语义）按实体/分区
  切分，多个 worker 各自消费不同分区，线性扩展吞吐。
- **管理平面多副本**：API 无状态，前置负载均衡即可多活。

### 2.2 故障检测与自动切换 (<3s)
- `/health` 探活（`api/serve.py`）。
- 集群选用 **Raft/共识**（生产，如 etcd）或健康探活+租约完成 leader 选举与故障切换；
  本仓库在逻辑层演示了 `CircuitBreaker` 的快速失败与降级切换（`bus`）。
- 单节点故障：请求经负载均衡转到健康副本，<3s 完成。

### 2.3 数据一致性（CAP 权衡与选择）
- **权衡**：检测/响应侧选 **AP（可用性优先）**，容忍短暂不一致，靠事件总线保证最终一致；
  审计链与策略数据选 **CP（强一致）**，因其不可篡改、需权威顺序。
- **多副本 + 异地容灾**：RPO < 1min（事件流近实时同步/异步的跨区复制），RTO < 5min
  （无状态节点秒级拉起 + 数据从异地副本恢复）。审计链可跨节点锚定到区块链/哈希链，
  保证异地不可抵赖。

## 3. 核心检测/分析引擎设计（如何做到 <50ms）

**数据流**：
```
原始事件 --normalize(脱敏)--> [Feature] --baseline.observe(在线统计)-->
z-score 多维异常评分 --rules(确定性护栏)--> 融合分数 -->
LLM 因果推理 (mock/http 可降级) --> 可解释输出 (归因+战术路径+建议)
```

**为什么能 <50ms**：
- **纯内存 + O(1) 在线递增统计**：行为基线用 Welford 在线算法，无需重扫历史（`baseline.py`）。
- **无阻塞 IO**：正常路径不落盘、不调外部服务（LLM 用可降级推理器，失败自动回退 mock）。
- **批量消费**：事件总线按批拉取（`batch_size`），减少上下文切换与函数调用开销。
- **无锁单线程消费**：单一 worker 内顺序处理，避免锁竞争（多 worker 并行按分区扩展）。
- 实测本仓库 demo（单线程）约 **17k~21k EPS / 单进程**，多 worker 线性扩展后满足 >100k EPS。

### 智能降噪（告警疲劳解药）
- 不是每条异常都上报；`DetectionPipeline` 综合 AI 分 + 规则信号 + 冷启动状态给出 `priority`
  （none/low/medium/high/critical）。正常流量（基线内）一律 `none`，只有显著偏离或规则命中才形成事件。
- 演示中 831 条遥测仅产生 31 条事件，其中大量被归并为同实体同类事件，真正做到「分析师只看该看的」。

## 4. 性能目标与量化验证方法

| 指标 | 目标 | 方法 |
|------|------|------|
| 吞吐 | >100k EPS | 多分区 + 无状态 worker 横向扩展；单 worker 约 20k EPS |
| 实时检测端到端延迟 | <50ms | 纯内存管线、批量消费、无阻塞 IO；demo 831 事件 39~49ms |
| 分析类复杂查询 | <2s (PB级) | 生产接入列存/OLAP（如 ClickHouse）做查询；本仓库聚焦检测路径 |
| 自动化响应 | <500ms | 决策层纯内存（`response/orchestrator.py`），动作下发经事件总线 |
| 资源效率 | CPU<70%/内存<80% (8C16G) | 背压缓冲上限、熔断、异步消费，防积压耗尽资源 |
| 对业务损耗 | <5% | 采集/检测为旁路(带外)路径，不阻塞业务主链路 |

> 详细基准方法见 [`docs/08-performance.md`](08-performance.md)。

## 5. 部署、监控与升级（概述）

- **一键部署**：`deploy/Dockerfile` + `deploy/docker-compose.yml`（开发/私有化）；
  生产多活用 Helm Chart / Terraform（见 `docs/05`）。
- **可观测性**：`/status`、`/health` 暴露探活与统计；审计链 `/audit/verify` 校验完整性。
- **零停机滚动升级**：无状态节点先起新版本、健康检查通过后逐批替换；策略/模型版本化灰度。
